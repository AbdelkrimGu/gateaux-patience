# 05 — Current Site Audit (pre-revamp)

> Technical + visual audit of the Gateaux Patience site as of commit `f4df6ca` (2026-10-04).
> Method: code reading, `npm run build`, production server (`next start -p 3123`), Lighthouse 12 (mobile, perf preset) and Playwright 1.63 screenshots (Pixel 7 + 1440×900 desktop) against **live MongoDB/S3 data**. No source, config or git state was modified.

---

## TL;DR

- **The back end is solid; the public front end is the weak part.** Keep the data layer (MongoDB + S3), the admin, next-intl routing and messages, the tiramisu engine, the SEO/JSON-LD and the `/contact` QR page. Rebuild the public UI: home, gallery, cake detail, header and footer.
- **The home page is slow on mobile.** Lighthouse mobile scores were 16–46 across four runs, with LCP 7.7–9.4 s, TBT 0.8–1.9 s, TTI 14–35 s and 15–39 s of main-thread work. The cause is JavaScript animation (framer-motion on dozens of elements, infinite loops, six `setInterval` image cyclers and scroll parallax), not page weight: only about 750 KB is transferred.
- **The brand fonts don't render.** `globals.css` redefines `--font-playfair`, `--font-inter` and `--font-cairo` on `:root` with literal family names, which override the hashed families next/font injects. At runtime only **Great Vibes** loads. Body text falls back to the system font (Segoe UI), headings to Georgia, and Arabic to Arial. This is confirmed via `document.fonts` and computed styles.
- **The hero hides its own message.** On mobile and desktop the H1 is below the fold, under a decorative logo constellation. It is rendered at `opacity:0`, its word-by-word animation starts 1.5 s after hydration, and there is no CTA above the fold.
- **Reliability bug:** the `/_next/image` request for the 256 px WebP of the 2.1 MB logo PNG **hung on all 3 attempts** on this server instance. As a result the desktop hero showed an empty white circle where the logo belongs. Pre-sized logo files already exist in `public/contact/`.
- **The category cards show no photos.** No category has an `image` in the database, so all 7 cards render rainbow placeholder gradients with a tag icon, which looks unfinished.
- **The best page on the site is the static `/contact`:** Lighthouse 95, 13 KB of HTML, 0 JS. It is a good benchmark for the revamp.
- **Dead weight to remove:**
  - 5 unused npm deps: `swiper`, `react-image-gallery`, `sonner`, `react-hook-form` + `@hookform/resolvers` + `zod`, `class-variance-authority`.
  - 2 experimental routes and their heroes: `hero-stories`, `hero-zellige`. ZelligeHero is the only reason `embla-carousel-autoplay` is installed.
  - The unused `StatsBar` component.
  - 6.8 MB of raw letter sprites, plus duplicate `/images` and `/Logo` folders at the repo root.
- **The screenshot-review loop works on Windows.** Chrome, Edge and Playwright Chromium (rev 1243, installed in 26 s) all run. Two caveats:
  - **Kaspersky** injects a 170 KB script into every page and intercepts TLS (`SELF_SIGNED_CERT_IN_CHAIN`). Block `*kaspersky-labs.com*` in every measurement.
  - Wait on `load` plus a fixed delay, never `networkidle`: the home page never goes network-idle.

### 3.1 Root causes on the home page

1. **Too much continuous JS animation.** Main-thread time breaks down into Other 6.7 s, Script Evaluation 3.6 s, Style & Layout 2.9 s and Rendering 1.2 s, and that is the *good* run. The framer-motion chunk alone costs 8.4–26 s of CPU time. Contributing factors:
   - 6 `CyclingImage` satellites, each with its own `setInterval` that swaps a `next/image`, so new network requests keep firing. **The page never reaches network-idle**: the Playwright `networkidle` wait timed out after 30 s on desktop.
   - A 6.5 s story rotation with a Ken-Burns `scale` on a `fill` image.
   - Infinite `animate` loops on the badge dot and the CTA arrow.
   - `useScroll` / `useTransform` parallax on two large blocks.
   - About 30 motion elements with staggered delays.
   - Lighthouse also flagged 2–7 non-composited animations.
   - **`prefers-reduced-motion` is ignored everywhere** except TiramisuPreview.
2. **The LCP is gated by the entrance animation.** The SSR HTML contains **24 `opacity:0` inline styles**. The H1 words animate in from 1.5 s **after hydration**, the story image from 2.2 s, and the CTAs from 2.5 s. On a throttled phone, hydration itself takes seconds, which is how LCP reaches about 8 s.
3. **The above-the-fold priority is wrong.** Two images are `priority`-preloaded:
   - the logo, as a 2.1 MB PNG source;
   - the story image, which sits **below the fold** on mobile.

   The preload `imageSrcSet` for the story offers widths up to 3840w.
4. **The logo optimiser hung.** `/_next/image?url=/Logo/Logo-Photoroom.png&w=256` with `Accept: image/webp` timed out on 3 of 3 attempts, while w=128, w=640 and PNG at 256 returned in under 170 ms. This is the desktop (DPR 1) variant, so the desktop hero showed **an empty white circle** in both the fold screenshot and the full-page screenshot. Even without the hang, transcoding a 2.1 MB PNG on demand is fragile. Serve the pre-sized `public/contact/logo-360.avif` and `logo-720` files.
5. **Satellite images are blurry on desktop.** The satellites declare `sizes="80px"` but render at about 120 CSS px on desktop, so they come out visibly soft (see the desktop screenshot).
6. **The HTML is 195 KB per home request.** The RSC payload serialises full cake documents with all translations and image arrays, including 24 category image groups for the satellites, and only a fraction of that is displayed.

### 3.2 Tiramisu configurator

- The page itself is fast (88).
- The cost arrives when a template is chosen: the canvas loads `templates/<shape>/base.png` raw, at **1.8–2.8 MB per PNG**, plus the letter sprite sheets.
- On a 3G phone in Algeria, that is several seconds before the preview appears.
- Pre-encode the bases as WebP/AVIF at 1–1.5k px (typically 150–300 KB) and keep the PNGs as build inputs outside `public/`.

### 3.3 `/contact`

- It is near-perfect: 0 JS, inline CSS, one AVIF logo.
- Its one flaw is CLS 0.138, caused by the `header.qc-hero` block. The likely cause is a logo `<img>` without reserved height, or a font swap.

## 4. Correctness, accessibility and RTL issues

### 4.1 Font loading bug (high impact, easy fix)

`globals.css` declares the following inside `@layer base`:

```css
:root {
  --font-playfair: "Playfair Display", Georgia, serif;
  --font-inter: "Inter", system-ui, sans-serif;
  --font-cairo: "Cairo", Arial, sans-serif;
}
```

next/font sets the same variables on `<html class="__variable_…">` with hashed family names (`__Inter_xxx` and so on). The `:root` rule wins, so the computed `font-family` is the literal `Inter, system-ui…`. Inter is not installed, so text falls back to Segoe UI on Windows and Roboto on Android. At runtime `document.fonts` showed **only Great Vibes loaded**. Every heading on the site is therefore Georgia, and Arabic is Arial. The screenshots confirm both.

The fix is to delete those three lines. In the revamp, reduce to two families at most and subset Arabic.

### 4.2 Accessibility

- **Motion:** the site has no `prefers-reduced-motion` handling (WCAG 2.3.3). It also has autoplaying rotations with no pause control (WCAG 2.2.2 "Pause, Stop, Hide").
- **Header:** the mobile menu button is `aria-label="Toggle menu"` in English in every locale, with no `aria-expanded` and no `aria-controls`. The language dropdown also lacks `aria-expanded`, and it has no `menu`/`listbox` semantics.
- **Modals:** the logo and category-picker modals have `aria-modal` but no focus trap or focus return, as far as code reading shows. Their close label is French in all locales.
- **Story dots:** 2 px tall buttons. The DOM probe found **13 interactive elements under 24×24 px** on the home page (WCAG 2.5.8).
- **Headings:** the H1 is split into per-word `inline-block` spans. Screen readers and the accessibility tree read it as `DesGâteauxquiRacontentVotreHistoire` (the textContent has no spaces, because spacing is done with CSS margins).
- **Alt text:** OK. All `<img>` have `alt`, and no links or buttons lack a name.
- **Contrast:** `text-charcoal-light` `#6B6B6B` on `#FFF8F3` is about 5:1 (OK). The 10–11 px uppercase tracking labels (`text-[9px]`/`[10px]`, `text-white/75` on photos) are too small to read. Rose `#C9727A` text on white is about 3.4:1, which **fails AA for body text** in the badges and links.

### 4.3 RTL

- Direction handling uses `isRTL` ternaries in 15 components, with `flex-row-reverse` ×29, `text-right` ×24 and `rotate-180` ×13. Only 9 logical utilities (`ms-/me-/ps-/pe-/start/end`) are used.
- **Bug pattern:** `<html dir="rtl">` already flips flex rows. Adding `flex-row-reverse` when `isRTL` flips them **back** to LTR order. The Footer does this 6 times (`flex-row-reverse justify-end`), so in Arabic the icons sit on the wrong side of their labels. The same pattern appears in the hero story caption and the story dots.
- Arabic headings are styled through `font-playfair` (Latin-only, now falling back to Georgia/Arial) instead of an Arabic display face. Arabic typography is therefore an afterthought.
- In `/ar` the satellite ring and the H1 render fine (symmetric layout). Most RTL bugs are in the asymmetric rows.
- **Revamp rule:** use logical properties only (`ms-*`, `ps-*`, `start-*`, `text-start`) and no `isRTL` class ternaries. Use `rtl:` variants only for icon mirroring.

### 4.4 Other code issues

- `mongodb.ts`: in production, `getClientPromise()` builds a new `MongoClient` each time `cachedPromise` is null. That is fine per instance, but `initialize()` (12 `createIndex` calls plus a seed check) runs on **every cold start**, which adds latency on Netlify functions. Move index creation into a script.
- Home rendering is `force-dynamic` with no caching, so every visit does 4 MongoDB queries. The revamp should use `revalidate` (ISR) or tag-based revalidation triggered from the admin.
- `HeroSection.tsx` is a 928-line client component. It contains the logo modal, the category picker modal, the satellites and the stories, and duplicates localisation logic.

## 5. Visual design critique (from the screenshots)

Screenshots are in the scratchpad: `m-*`/`d-*` × `early`/`fold`/`full`, plus slices.

**What works**

- The palette (cream, dusty rose, gold) suits a feminine cake atelier, and the script wordmark is charming.
- The cake photography is the real asset: colourful, personal, with names on the cakes.
- The gallery grid on desktop (4 columns, category chip, a "Commander" WhatsApp pill on each card) is clean and usable.
- The `/contact` page (dark, copper logo, big green WhatsApp button) is the most premium and most conversion-focused screen on the site.

**What doesn't**

1. **The hero is about the logo, not the cakes.** On a Pixel 7 the whole first screen is a gold orbital diagram around a dark logo disc with six tiny thumbnails. The H1 starts at about 1.4 viewports, and the first full-size cake photo and the CTA are about 2.5 viewports down. On desktop the fold is only the ring, which in our run had **an empty centre** because of the logo hang. A visitor sees no headline, no offer and no button.
2. **There are two competing brand identities.** The dark copper/black 3D logo (also used on `/contact`) clashes with the light cream/rose site. The revamp should pick one direction. The dark copper of `/contact` looks more distinctive.
3. **Every section uses the same template:** pill badge, then a big serif title ("Chefs-d'Œuvre Sucrés", "Pour Chaque Occasion", "Simple & Facile"), then a grey subtitle, then a stack of cards. It reads as a generic SaaS-landing template and has no rhythm.
4. **The mobile home page is 11,240 px tall, about 13 screens.** The six featured cakes stack as full-width cards, then come seven category cards and four "how to order" steps, each on its own row.
5. **The categories look broken.** Seven rainbow-gradient cards (sky blue, mustard, violet, teal…) with a generic tag icon. The colours are off-brand and there are no photos, because no category has an image set in the admin.
6. **Fonts:** the faces actually rendered are system-default (§4.1), which makes the site feel cheaper than intended.
7. **Copy:** "Devis sur demande" repeated under every featured card adds noise. Mixed "Tarte"/"Gâteau" naming in the titles is a data-quality issue, not a UI one.
8. **Floating WhatsApp bubbles** sit on every featured card's image corner and compete with the cake.
9. **The tiramisu wizard entry is clean but empty.** About 40% of the first screen is blank above the question.

**Environment gotchas to bake into the loop**

1. **Kaspersky Web Anti-Virus** injects `gc.kis.v2.scr.kaspersky-labs.com/.../main.js` (170 KB) into every HTML page, including localhost, and does TLS interception.
   - It **skews Lighthouse**: TBT doubles and the home main-thread time goes from 15 s to 37 s.
   - Always run Lighthouse with `--blocked-url-patterns="*kaspersky-labs.com*"`.
   - In Playwright, use `context.route(/kaspersky-labs\.com/, r => r.abort())`.
   - For npm/Playwright downloads, either whitelist localhost and the registries in Kaspersky, or set `NODE_EXTRA_CA_CERTS` to Kaspersky's root certificate.
2. **Don't wait for `networkidle`** on the current home page (the satellites never go idle). Use `load` plus a fixed wait, and design the new site so it *does* go idle.
3. **Locale cookie:** use a fresh browser context per locale, or set `NEXT_LOCALE` explicitly. Otherwise `/galerie` renders in whichever language was visited last.
4. **Git Bash path mangling:** set `MSYS_NO_PATHCONV=1` when passing URL paths like `/fr` to native tools, or run them from PowerShell.
5. `npm run build` is safe to repeat: the `prebuild` QR regeneration is deterministic and left no diff.

**Recommended loop:** a `scripts/shoot.mjs` (or a scratch tool) that does the following:

1. Start `next start` on a fixed port.
2. For each route × {Pixel 7, 1440×900} × {fr, ar}, take a fold screenshot and a sliced full-page screenshot with Kaspersky blocked.
3. Optionally run Lighthouse with the block pattern.
4. Write the PNGs and a JSON summary for review.

Each full pass over about 5 routes takes roughly 2–3 minutes without Lighthouse and 6–8 minutes with it.
